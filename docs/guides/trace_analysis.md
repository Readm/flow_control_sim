# Go Execution Trace Analysis Guide

This guide explains how to use Go's execution tracer to analyze synchronization bottlenecks in `flow_sim`.

## 1. Prerequisites
You need the `trace.out` (or `trace_16.out`) file generated by the benchmark.

**Command to generating trace:**
```bash
go test -bench="BenchmarkRingCoreScaling/Cores_16$" -run=^$ -benchtime=100x -trace=trace_16.out ./internal/core/network -args -bench_nodes=20
```

## 2. Opening the Trace Tool
Run the following command in your terminal:
```bash
go tool trace trace_16.out
```
This will start a local web server (usually at `http://127.0.0.1:XXXX`) and open it in your default browser.

## 3. Key Views

### A. View Trace (The Timeline)
Click on **"View trace"**. This is the most important view.

*   **Navigation**:
    *   `W` / `S` to Zoom In/Out.
    *   `A` / `D` to Pan Left/Right.
*   **Rows**:
    *   **PROCS**: Shows logical processors (P). The number of rows equals `GOMAXPROCS`.
    *   **GOROUTINES**: Shows specific Goroutines (G).
*   **Colors**:
    *   **Green**: User code executing.
    *   **Red**: Blocking (Network/Channel/Select).
    *   **Blue**: Scheduling/System calls.
*   **What to look for**:
    *   **"Sawtooth" Pattern**: You should see periods of dense activity (Simulated Work) followed by gaps (Global Barrier Wait).
    *   **Gap Width**: The empty space between blocks of activity represents the **Synchronization Overhead**. If one core finishes early (short green bar), it sits idle until the last core finishes.

### B. Synchronization Blocking Profile
Click on **"Synchronization blocking profile"**.

*   This graph shows *where* goroutines are waiting.
*   In `flow_sim`, you will likely see a huge box for `runtime.chanrecv1` pointing to `ComponentSync.WaitDone`.
*   This confirms that the threads are blocked waiting for the global barrier signal.

### C. Goroutine Analysis
Click on **"Goroutine analysis"**.

*   Select the Goroutine type corresponding to Worker Nodes (usually `github.com/Readm/flow_sim/internal/core/network...`).
*   It lists individual Goroutine statistics.
*   **Scheduler Wait Time**: Time spent waiting for a P (Processor). High values indicate CPU saturation or strict scheduling contention.
*   **Sync Block Time**: Time spent waiting on Channels/Mutexes. High values indicate data dependency or barrier stalls.

## 4. Case Study: 16-Core Bottleneck
In the 16-core trace (`trace_16.out`), observe the **PROCS** timeline:
1.  Identify the **AdvanceTo** cycle boundaries.
2.  Notice that as cores finish their work (Green bars end), they enter a waiting state.
3.  The *slowest* core determines the start of the next cycle.
4.  With 16 cores, the probability of one core having a "long tail" random spin (e.g., closer to 20us) is high, forcing the other 15 cores (some of which ran for only 5us) to wait.
5.  **Conclusion**: The efficiency loss is primarily due to **Load Imbalance** combined with **Global Barrier Synchronization**.
