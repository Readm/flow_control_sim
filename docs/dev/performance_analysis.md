# 50节点环型测试性能分析报告

本文档记录了基于 50 个节点的环型拓扑（Ring Topology）在异步模拟模型下的性能评估及瓶颈分析。

## 1. 测试环境
- **节点数量**: 50
- **链路延迟**: 10 Cycles
- **注包间隔**: 每 3 Cycles
- **模拟时长**: 10,000 Cycles
- **硬件环境**: 16 核 CPU (GOMAXPROCS=16)

## 2. 性能数据对比 (优化前后)

| 指标 | 优化前 (`sync.Cond`) | 优化后 (Atomic + Channel) | 变化 |
| :--- | :--- | :--- | :--- |
| **单核吞吐量** | 7,990 Cycles/Sec | **8,216** Cycles/Sec | **+2.8%** |
| **多核吞吐量** | 25,554 Cycles/Sec | 25,410 Cycles/Sec | 持平 |
| **同步层 CPU 占比** | **13.13%** | **3.38%** | **下降 74%** |
| **互斥锁竞争延迟** | ~23ms (排行第 1) | **跌出前 10** | **极大改善** |

## 3. 当前瓶颈分析 (New Bottlenecks)

在消除了 `ComponentSync` 的锁竞争后，系统的性能瓶颈发生了转移。目前的瓶颈主要集中在以下三个方面：

### 3.1 内存分配与切片操作 (Memory Management)
- **`runtime.mallocgc` & `runtime.growslice` (~15% CPU)**: 
    - 系统在 `Port` 接收、`Link` 处理以及 `InputQueue` 存取过程中，产生了大量的临时切片（`[]packet.Packet`）。
    - 频繁的 `append` 操作导致底层数组不断重分配。
    - 内存分配压力不仅消耗 CPU，还增加了 GC（垃圾回收）的工作量。

### 3.2 运行时调度开销 (Go Runtime Scheduling)
- **`runtime.findRunnable` / `runtime.park_m` / `runtime.mcall` (>40% 累计时间)**:
    - 对于 50 个节点及相关 Link，系统中存在数百个活跃的 Goroutine。
    - 信号机制（Channel 通知）虽然比广播轻量，但频繁的 `unpark` 和 `park` 依然给 Go 调度器带来了沉重负担。每个周期所有组件都在休眠和苏醒之间循环。
- **`runtime.futex` 操作**: 内核态的线程同步操作在极高频的异步通信中比例依然显著。

### 3.3 细粒度任务处理
- **`BaseNode.Advance` / `Link.Advance`**: 
    - 任务粒度非常小（每个 Tick 处理几个包），导致执行实际业务逻辑的时间远小于调度和维护状态机的时间。

## 4. 深度优化建议 (Next Steps)

针对新的瓶颈，建议采取以下策略：

### 4.1 引入对象池 (Packet Pooling)
- **优化点**: 所有的包列表 (`[]packet.Packet`) 应该从 `sync.Pool` 中获取。
- **目标**: 将 `mallocgc` 的消耗降至 2% 以下，显著降低 GC 频率。

### 4.2 任务聚合 (Coarsening Task Granularity)
- **优化点**: 增加 `Advance` 的步长，或者将互联紧密的组件分配到同一个 Goroutine（线性调度）。
- **理由**: 让一个协程连续处理多个周期或多个串联组件，减少在 Go 调度器中的反复排队。

### 4.3 零拷贝端口设计
- **优化点**: 目前 `Port` 内部通过缓存和排空来保证正确性。可以探索基于循环缓冲区（Ring Buffer）的直接共享内存模式。
- **目标**: 消除 `drainChannel` 过程中的数据拷贝。

## 5. 总结
`ComponentSync` 的优化成功扫清了同步层的阻塞障碍。目前系统的性能表现受限于通用的系统级开销（内存与调度）。下一步优化的重点应从“减少锁”转向“减少分配”和“提高任务局部性”。
## 6. 附加测试：模拟计算负载 (Spin-Wait)

为了验证在有实际业务负载情况下的并行效率，我们为每个节点添加了 **5~20µs 的随机自旋延迟**（模拟 GEM5 O3 CPU 核心执行时间）。

| 指标 | 单核 (GOMAXPROCS=1) | 16核 (GOMAXPROCS=16) | 加速比 (Speedup) |
| :--- | :--- | :--- | :--- |
| **吞吐量 (Cycles/Sec)** | 1,324 | **11,065** | **8.36x** |
| **平均单周期耗时** | 755µs | 90µs | - |

**分析结论：**
- **加速比大幅提升**：从纯同步开销阶段的 3.1x 提升至 **8.36x**。
- **调度开销占比下降**：当业务逻辑（自旋）增加时，Go 调度器的固定开销被稀释。
- **扩展性瓶颈**：16 核达到 8.36x 意味着并行效率约为 52%。这说明在 10µs 级别的任务粒度下，系统已经具备了较好的多核扩展能力，但仍受限于内部通信延迟。
